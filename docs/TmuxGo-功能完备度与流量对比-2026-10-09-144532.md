# TmuxGo 功能完备度与流量对比

- 评估时间：2026-10-09 14:45:32（Asia/Shanghai）
- 评估范围：当前代码、终端传输实现、已有测试与协议文档

## 结论

TmuxGo 已经不是功能 Demo，而是一个功能覆盖比较完整、可以日常使用的个人或小团队远程工作台。

- 核心功能完整度：约 8.5/10
- 终端与 tmux 工作流：约 9/10
- 生产可靠性与可观测性：约 7/10
- 弱网和流量优化：已有较完整基础，但缺少与直连 SSH 的系统性实测数据

当前重点不应是继续盲目增加功能，而应转向真实弱网验证、流量基准、长时间稳定性和文档一致性。

## 流量优化现状

### 二进制终端帧

前端默认协商：

```json
{
  "binaryOutput": true,
  "compressOutput": "gzip",
  "cellOutput": true,
  "compactHeader": true
}
```

相关位置：

- `apps/frontend/src/hooks/useWebSocket.ts`
- `apps/frontend/src/hooks/useSessionSocket.ts`
- `apps/gateway/src/lib/stream-binary.ts`

二进制帧减少了 JSON 转义、字符串封装以及 host/session 的重复传输。

### gzip

服务端只压缩达到阈值的输出。压缩后如果没有变小，会回退到明文，避免小帧和高熵数据产生负收益。

仓库中的传输 benchmark 结果：

| 场景 | 原始 ANSI | gzip 后 |
|---|---:|---:|
| 普通短输出 | 39 B | 不压缩 |
| spinner 模拟 | 851 B | 199 B |
| 全屏重绘 | 32,827 B | 304 B |

这说明 gzip 对重复度高的大块终端输出效果明显，但不能据此推导所有场景的平均节省比例。

### compact header

普通帧会重复携带 `hostId + sessionName`。compact header 使用连接级 route 字典，用 2 字节 route index 替代重复字符串，主要优化高频小帧。

### 输出批处理

当前 profile：

```ts
foreground: { flushInterval: 4, maxChars: 65536 }
background: { flushInterval: 32, maxChars: 24576 }
mobile: { flushInterval: 24, maxChars: 16384 }
```

后台页面和移动端会降低刷新频率并限制单次发送量。

### cell 模式的注意点

cell 模式不一定总是比 ANSI 更省。短输出场景中，cell snapshot 可能因为包含尺寸、光标、颜色和属性等结构化信息而更大；cell diff 更适合持续更新、局部变化的 TUI 画面。

## 与直连 SSH 的比较

### Gateway 与远端主机在同一台服务器

```text
浏览器 → Gateway / 远端主机
```

此时 TmuxGo 的 WAN 链路是浏览器到 Gateway，终端输出采用 binary + gzip，通常表现较好。

- 少量交互：直连 SSH 可能略省
- 大量重复日志：TmuxGo 可能明显省
- 全屏 TUI：取决于 cell 模式和重绘方式
- 小输出：TmuxGo 有额外 WebSocket 和协议头开销
- 延迟：直连 SSH 通常更直接

### Gateway 在本地，远端主机在另一台服务器

```text
浏览器 → 本地 Gateway → SSH → 远端主机
```

这时相比直连 SSH 多了一跳，因此总字节数不一定更少，端到端延迟也可能略高。TmuxGo 的主要价值会更多体现在：

- 浏览器和移动端随时接入
- 多主机统一管理
- Session、文件、Git、Agent、MCP 集成
- 多客户端共享
- 断线后快速恢复

### TmuxGo 的远端 SSH 压缩

远程 terminal attach 会请求：

```text
-o Compression=yes
```

位置：`apps/gateway/src/lib/terminal-attachment.ts`

远程场景大致是：

```text
远端主机 ← SSH 压缩 → Gateway ← gzip/binary WebSocket → 浏览器
```

两条链路分别压缩，不能简单把两个压缩比例相乘作为总收益。

## 综合判断

可以将当前流量表现概括为：

> 比未压缩的 WebSocket/ANSI 方案省很多；和开启压缩的直连 SSH 相比，终端流量大致接近，是否更省取决于 Gateway 部署位置、输出类型和是否启用 cell 模式。

## 最值得优先做的三件事

1. 补 TmuxGo 与直连 SSH 的流量、延迟、CPU 对照 benchmark。
2. 修正文档与实现不一致，特别是压缩阈值和 cell 默认开关。
3. 将已有流量指标做成可见的网络诊断面板。
